# FactoMCP acceptance test for the seamed autonomous mall

This file is an **in-game acceptance-test contract** for an automated agent such as Codex CLI
connected to a local Factorio instance through FactoMCP.

The object under test is the preferred two-worker prototype generated by
`examples.autonomous_mall/seamed_worker_pool.py`. The purpose is to test the behavior of the
**real placed blueprint in Factorio**, including circuit propagation, requester-chest setpoints,
logistic delivery, assembler control, worker dispatch, and the stop-and-wait protocol.

Do not replace these tests with Python semantic simulation. The Python tests already cover the
abstract circuit; this procedure is specifically intended to catch mistakes that only appear after
physical lowering and placement.

## Instructions for the testing agent

At the beginning of the run, inspect the FactoMCP tools that are actually available and map the
operations in this document onto them. Tool names are deliberately not hard-coded here because the
server API may change.

Use FactoMCP to perform as much of the procedure as possible. If a required observation or mutation
is not supported by the available tools, report that test as **UNSUPPORTED**, explain which primitive
is missing, and continue with the remaining tests. Do not invent observations.

The agent may use editor/cheat facilities to create power, roboports, robots, source chests, items,
and a clean test area. However, do **not** shortcut the behavior under test:

- do not insert ingredients directly into a mall requester chest when testing requester demand;
- do not insert products directly into the mall provider chest;
- do not set an assembler recipe manually;
- do not manually enable/disable a mall assembler;
- do not edit internal combinators or internal wires;
- do not merge external ABI lanes merely to make probing easier.

It is fine to insert ingredients into a separate storage/passive-provider/source chest inside the
same logistic network. That preserves the requester/bot path being tested.

When a test says to "wait until stable", advance enough game ticks for circuit propagation and
logistic/assembler activity to settle. Prefer observing a condition rather than assuming a fixed
number of ticks. Use a generous timeout and report a timeout as a failure with the last observed
state.

## Build the blueprint

From the repository root:

```bash
uv run python -m examples.autonomous_mall.seamed_worker_pool \
  --workers 2 > mall-workers.txt
```

Use the generated blueprint string from `mall-workers.txt`. Do not reuse an older blueprint string.

Place it in a clear area with enough room around the worker assemblers and the exposed top seam.
Power the complete blueprint.

## Physical shape and external ABI

The expected topology is:

```text
             external ABI
                  │
              [ HEAD ]
                  │
       [worker controller 0] ── [assembler 0]
                  │
       [worker controller 1] ── [assembler 1]
                  │
              [ TAIL ]
```

There must be exactly two worker assemblers, two mall requester chests, and two mall active-provider
chests.

The exposed external seam is the topmost row. From left to right its ten lanes are:

```text
1  offer_valid
2  offer_blocked
3  offer_accepted
4  busy_count
5  completion_count
6  offer_recipe
7  offer_inputs
8  offer_product
9  reserved
10 promised
```

The four input lanes are:

```text
offer_valid
offer_recipe
offer_inputs
offer_product
```

The other six lanes are observations from the mall.

Keep the four input networks electrically separate. In particular, do not connect recipe, inputs,
and product onto one common green circuit network. Keep `reserved` and `promised` separate when
observing them.

If FactoMCP exposes entity descriptions, prefer them to raw coordinates when locating ports and
worker devices. Otherwise use the exposed top-row ordering above plus spatial association of each
assembler with its controller.

## Test environment

Create one powered logistic network covering both worker requester/provider cells. It should contain
at least one roboport and enough logistic robots to deliver a few items promptly.

Create a separate logistic source chest in that network. Tests will add or remove iron plates and
copper plates from this source chest. The source chest is test infrastructure and is not part of the
mall blueprint.

Before each test that requires a clean start:

1. set external `offer_valid` (`signal-V`) to 0;
2. wait until the mall has no active job, unless the test intentionally carries jobs across phases;
3. empty both mall provider chests;
4. remove test ingredients from the logistic source chest;
5. clear stale logistic deliveries from requester chests if necessary;
6. configure the three vector inputs while `V=0`;
7. wait briefly for the low phase to propagate before raising `V` again.

Do not tear down and replace the mall blueprint between phases of one test; state continuity is part
of the protocol being tested.

## Signal conventions used below

The first test job is one iron-gear-wheel craft:

```text
offer_recipe:
    iron-gear-wheel = 1

offer_inputs:
    iron-plate = 2

offer_product:
    iron-gear-wheel = 1
```

The second job is one copper-cable craft:

```text
offer_recipe:
    copper-cable = 1

offer_inputs:
    copper-plate = 1

offer_product:
    copper-cable = 2
```

`offer_valid` is `signal-V`. The generated mall treats one accepted envelope as **exactly one
craft**, not one item and not an arbitrary batch.

# Acceptance tests

## T0 — Structural and ABI sanity

### Setup

Place and power the freshly generated two-worker blueprint.

### Observe

Verify:

- exactly two assembling-machine-3 entities belong to the mall worker cells;
- exactly two requester chests belong to the mall worker cells;
- exactly two active-provider chests belong to the mall worker cells;
- all ten external docks form one visibly exposed top row;
- the `offer_valid` dock is electrically connected inward;
- `offer_recipe`, `offer_inputs`, and `offer_product` are distinct external lanes rather than a
  hidden or merged network.

### Pass condition

All observations above hold and there are no obviously overlapping/unplaceable mall entities.

---

## T1 — Critical regression: recipe and requester demand are captured together

This is the highest-priority test. It catches the previously observed failure where the recipe was
configured but the reservation vector arrived too late, leaving the requester chest with no demand.

### Setup

- Ensure no iron plates are available anywhere in the test logistic network.
- Set `V=0`.
- Configure the iron-gear job exactly as specified above.
- Wait for the low phase to settle.

### Stimulus

Set `V=1` and leave it high.

### Observe

Wait until worker 0 accepts the job. Then inspect all of the following **before supplying iron**:

- worker 0 assembler recipe is `iron-gear-wheel`;
- worker 0 requester chest has a circuit/logistic request for exactly 2 iron plates;
- external `reserved` contains `iron-plate = 2`;
- external `promised` contains `iron-gear-wheel = 1`;
- external `busy_count = 1`;
- worker 1 remains idle.

If FactoMCP permits tick-level circuit observation, additionally verify the intended ordering:

1. the recipe/input/product packet becomes visible downstream;
2. only on a later reaction does the scalar probe cause acceptance.

The tick-level check is optional; the five state observations above are mandatory.

### Pass condition

Recipe, requester demand, reservation, promise, and busy state all describe the **same gear job**.
It is a failure if the recipe is configured while requester demand or `reserved` is empty.

---

## T2 — One accepted envelope performs exactly one craft

Continue directly from T1; keep the same accepted gear job.

### Stimulus

Add a reasonable supply of iron plates to the separate logistic source chest. Do not put them in the
mall requester chest manually.

### Observe

The expected lifecycle is:

1. logistic robots deliver iron plates to worker 0's requester chest;
2. the assembler begins one iron-gear-wheel craft;
3. while the craft is active, the controller withdraws the recipe/requester command used to start it,
   while the logical reservation/promise remain owned by the worker;
4. the craft finishes and the output inserter moves the product into worker 0's active-provider chest;
5. worker 0 returns idle.

At final stable state verify:

```text
worker 0 provider: exactly 1 iron-gear-wheel
busy_count:         0
reserved:           empty
promised:           empty
```

`completion_count` is a short event/pulse. If FactoMCP can sample it reliably, verify that one
completion was observed. Do not fail the otherwise successful test solely because the MCP interface
cannot catch a short pulse.

### Pass condition

Exactly one gear is produced and the worker releases all reservation/promise state afterward.

---

## T3 — Held-valid duplicate suppression

This test verifies the four-phase external contract.

### Setup

Use a clean gear job with ample iron plates available. Set `V=0`, configure the job, settle, then
raise `V=1`.

### Stimulus

After the first gear is accepted and completed, **do not lower `V`**. Leave the identical external
envelope held high for long enough that a second craft would certainly have started if the head were
retriggering it.

### Observe

The total new output caused by this high phase must remain exactly one gear.

Then:

1. set `V=0`;
2. wait for the low phase to propagate;
3. leave the same gear packet configured;
4. set `V=1` again.

### Pass condition

- first high phase produces exactly one gear;
- holding `V=1` does not produce another gear;
- after a real low phase and a second rising high phase, exactly one additional gear is produced.

Expected cumulative output after both high phases: exactly 2 gears.

---

## T4 — Busy worker forwards the next job to worker 1

### Phase A: occupy worker 0

Start from clean state with no iron or copper available.

Configure the gear job and raise `V=1`.

Wait for worker 0 to accept it while starved for iron. Verify:

```text
busy_count = 1
reserved   = { iron-plate: 2 }
promised   = { iron-gear-wheel: 1 }
```

Lower `V=0` and wait for re-arm. Do not supply iron.

### Phase B: submit a different job

Configure the copper-cable job while `V=0`. Put copper plates, but still no iron plates, in the
logistic source chest. Raise `V=1`.

### Observe

Worker 0 is already busy, so the probe must pass through it and worker 1 must accept the cable job.
Verify the aggregate state becomes:

```text
busy_count = 2

reserved:
    iron-plate   = 2
    copper-plate = 1

promised:
    iron-gear-wheel = 1
    copper-cable     = 2
```

Verify worker 1, not worker 0, configures `copper-cable`, requests copper, and produces exactly
2 copper cable into its provider chest.

After worker 1 completes while worker 0 remains starved, verify:

```text
busy_count = 1
reserved   = { iron-plate: 2 }
promised   = { iron-gear-wheel: 1 }
```

Finally add iron plates. Worker 0 should finish its original gear job and all ledgers should return
to empty.

### Pass condition

The two simultaneously outstanding jobs remain distinct, the second job is handled by worker 1, and
aggregate reservation/promise accounting tracks both jobs without duplication or loss.

---

## T5 — Both workers busy produces `blocked`, then the held offer retries automatically

This verifies the full HEAD -> workers -> TAIL -> HEAD stop-and-wait path.

### Phase A: make both workers busy and starved

1. With no iron/copper available, submit a gear job so worker 0 holds it.
2. Perform a proper `V=0` re-arm.
3. Submit a copper-cable job so worker 1 holds it.
4. Perform another proper `V=0` re-arm.

Verify `busy_count = 2`.

### Phase B: submit a third job while both are busy

Configure another gear job and set `V=1`. Keep this third offer held high.

### Observe blocked state

Because both workers are busy, the probe must reach TAIL. Verify:

```text
offer_blocked  = asserted
offer_accepted = not asserted for the third offer
busy_count     = 2
```

The exact duration of a short response signal may depend on where the MCP observation is made, but
the head's externally visible blocked state should remain observable while the third offer is held
valid and no worker can accept it.

### Phase C: free one worker without changing the third offer

Do **not** lower or rewrite the third external offer.

Add copper plates only. Worker 1 should finish its older cable job and become idle. Iron must remain
unavailable, so worker 0 remains occupied by its original gear job.

The head should automatically retry the still-held third gear offer. The newly idle worker 1 should
then accept it even though `V` was never toggled for the third offer.

### Pass condition

After worker 1 becomes free:

- the third offer is eventually accepted automatically;
- `offer_blocked` clears after acceptance propagates;
- worker 1 becomes busy with the third gear job;
- the third job is not duplicated into both workers.

At that point both workers may legitimately be waiting for iron. Supplying iron should allow both
one-craft gear jobs to complete, for exactly two gears total from those two outstanding gear jobs.

---

# Optional diagnostic test: packet-before-probe timing

Run this only if FactoMCP can inspect circuit networks at a sufficiently fine tick/reaction level.

With a clean mall and the gear packet configured under `V=0`:

1. sample the forward recipe/input/product lanes below HEAD and the forward `offer_valid` probe lane;
2. raise external `V=1`;
3. step/snapshot successive ticks or logical reactions.

The intended ordering is:

```text
packet vectors become nonzero
        ↓
remain stable
        ↓
probe becomes nonzero later
```

In particular, `offer_inputs = iron-plate:2` must not first appear *after* the probe that can cause a
worker to claim the job.

A failure here should be reported even if a particular run happened to craft correctly, because the
packet/probe ordering is a protocol invariant intended to tolerate physical lane skew.

# Failure signatures and likely subsystem

Use this table when reporting a failure; it is diagnostic guidance, not permission to modify the
blueprint during the acceptance run.

| Symptom | Likely area |
| --- | --- |
| recipe is set but requester demand and `reserved` are empty | packet/probe skew or worker reservation capture |
| `reserved` is correct but requester chest receives no request | worker -> `device_requester_demand` seam / AssemblerDevice demand path |
| one `V=1` high phase produces multiple crafts | HEAD accepted-offer suppression / four-phase protocol |
| worker 0 busy and worker 1 never accepts next offer | worker forward/probe seam |
| both busy but `offer_blocked` never becomes observable | TAIL reverse response or HEAD blocked latch |
| blocked offer does not retry after one worker becomes idle | HEAD stop-and-wait retry state |
| reservation/promise disappear while a worker is still active | worker lifecycle / `working` observation |
| correct request exists but no item is delivered | logistic-network setup, robot availability, or requester logistics rather than mall dispatch |

# Required test report

At the end, produce a concise report with one row per test:

```text
T0 structural sanity                  PASS / FAIL / UNSUPPORTED
T1 recipe + requester capture         PASS / FAIL / UNSUPPORTED
T2 exactly one craft                  PASS / FAIL / UNSUPPORTED
T3 held-valid duplicate suppression   PASS / FAIL / UNSUPPORTED
T4 second-worker forwarding           PASS / FAIL / UNSUPPORTED
T5 blocked + automatic retry          PASS / FAIL / UNSUPPORTED
```

For every failure include:

- the exact stimulus already applied;
- the last observed values of `busy_count`, `reserved`, `promised`, `offer_accepted`, and
  `offer_blocked` where available;
- assembler recipes and requester demands for both workers;
- relevant provider/requester inventories;
- game tick/time if the MCP exposes it;
- entity coordinates/descriptions needed to identify the failing lane or worker;
- whether the failure is deterministic when repeated from a clean state.

Do not fix source code as part of this acceptance procedure unless explicitly asked. The first run
should preserve the failure state and report evidence so the compiler/protocol bug can be diagnosed
from the real game behavior.

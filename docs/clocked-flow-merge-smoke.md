# Clocked Flow in-game merge smoke

This is the final manual Factorio check for the Clocked Flow Semantics milestone. It targets the
physical timing boundaries that are hardest for a Python simulator to validate independently of the
game.

## Generate both blueprints

From the merge candidate:

```fish
uv run python examples/clocked_flow_ingame_smoke.py
```

The script now prints:

1. the concrete scalar signal allocation used by the compiled circuit;
2. the required wire color for each driver-to-input connection;
3. the scalar/vector output ports and their physical phases;
4. a **schedule-driver blueprint string**;
5. the **compiled smoke-circuit blueprint string**.

Import both blueprint strings into Factorio.

The compiled circuit has these logical ports:

```text
inputs
  enabled          Level scalar
  source           vector Event payload
  source__valid    one-tick Event occurrence pulse
  tick             scalar Event payload (unused by this test)
  tick__valid      one-tick parent-clock occurrence pulse

outputs
  tail             source.step(1) payload
  tail__valid
  held             HoldInto(source, gated_tick)
  held__valid
  window           SumInto(source, gated_tick)
  window__valid
```

`source` is a whole-vector input, so ordinary item signals can be placed directly on that input
network.

## Connect the self-driving schedule source

The driver blueprint contains four empty constant combinators used as labeled output terminals. Each
terminal description names its destination and the required wire color. Make exactly these four
connections:

```text
DRIVER OUTPUT source         -> INPUT source
DRIVER OUTPUT source__valid  -> INPUT source__valid
DRIVER OUTPUT tick__valid    -> INPUT tick__valid
DRIVER OUTPUT enabled        -> INPUT enabled
```

Use the RED/GREEN color written on the driver terminal. The script also prints the same wiring list in
the terminal.

Leave compiled `INPUT tick` unwired. The test uses `tick` only as a clock, so its scalar payload is
irrelevant; `tick__valid` is the occurrence signal that matters.

Finally, connect the driver's substation to your electric grid. The compiled blueprint should be
powered in the usual way as well.

No other schedule circuitry is required.

## What the driver generates

Internally the driver uses a free-running counter and

```text
P = C mod 240
```

then emits one-tick pulses from decider combinators at the following phase conditions:

| driver P | source payload | source valid | tick valid | enabled |
|---:|---|---:|---:|---:|
| 20  | iron-plate = 5   | 1 | 0 | 0 |
| 80  | copper-plate = 7 | 1 | 1 | 1 |
| 120 | —                | 0 | 1 | 0 |
| 140 | iron-plate = 3   | 1 | 0 | 0 |
| 200 | —                | 0 | 1 | 1 |

The pulse-generator deciders themselves add one Factorio tick. Therefore treat the table as the
**driver's phase conditions**, not as an absolute game-tick number at the compiled input marker. All
signals belonging to one row are generated by equal-depth deciders, so their simultaneity is the
property under test.

The 240-tick repeat is intentionally much slower than the declared minimum separations.

## Expected observations

The generated outputs have physical pipeline phases. The smoke script prints those phases. Compare
payload and `__valid` at the output markers, and account for the printed phase from the actual input
pulse arrival. Do not expect an output to appear on the same game tick as its driver phase condition.

### 1. Event `.step(1)`

`tail` suppresses the first source occurrence of the **whole run**.

During the first cycle:

```text
first source occurrence:   iron-plate = 5    -> no tail Event
second source occurrence:  copper-plate = 7  -> tail Event copper-plate = 7
third source occurrence:   iron-plate = 3    -> tail Event iron-plate = 3
```

After that first suppression, every later source occurrence continues normally. In particular, when
the driver repeats after 240 ticks, the next `iron-plate = 5` occurrence must appear on `tail`; the
suppression must **not** reset each cycle.

### 2. GateClock

The raw `tick` occurrence generated from driver `P=120` has `enabled=0`, so it is removed by
`GateClock`.

There must be no `held__valid` or `window__valid` occurrence caused by that middle tick. The target
clock therefore advances from the enabled `P=80` occurrence directly to the enabled `P=200`
occurrence.

### 3. HoldInto simultaneous boundary

The `copper-plate = 7` source occurrence and the first enabled target occurrence are generated from
the same `P=80` row.

`HoldInto` is strict-prior, so the first `held` Event must be:

```text
iron-plate = 5
```

The simultaneous copper payload is too new for that target. At the later enabled target generated
from `P=200`, the most recent source is the `P=140` iron occurrence, so the second `held` Event must
be:

```text
iron-plate = 3
```

### 4. SumInto simultaneous boundary and gated interval

`SumInto` uses the semantic interval

```text
(previous target, current target]
```

Therefore the source occurrence simultaneous with the `P=80` target belongs to the current sum. The
first `window` Event must contain:

```text
iron-plate   = 5
copper-plate = 7
```

The raw target generated from `P=120` is gated away, so it must not snapshot or clear the interval
accumulator. The source generated from `P=140` remains accumulated until the next enabled target.
The second `window` Event must therefore be:

```text
iron-plate = 3
```

### 5. VALID alignment

For every `tail`, `held`, and `window` occurrence, its corresponding `__valid` pulse must arrive on
the same game tick as the payload at the output marker. Between occurrences, the VALID output is
zero.

## Compact pass checklist

A successful first cycle looks logically like this:

| driver row | `tail` | `held` | `window` |
|---:|---|---|---|
| P=20 source | suppressed | — | — |
| P=80 source + enabled target | copper = 7 | iron = 5 | iron = 5, copper = 7 |
| P=120 disabled target | — | no occurrence | no occurrence |
| P=140 source | iron = 3 | — | — |
| P=200 enabled target | — | iron = 3 | iron = 3 |

The actual output ticks are later by the physical phases printed by the generator.

## Merge decision

If all five observations match, this is sufficient as the final manual game-level smoke test for the
milestone. The automated suite already performs broader irregular-schedule coverage, including the
multi-rate Event ledger; this manual test is deliberately focused on confirming that Factorio's real
combinator update timing agrees with the compiler's most delicate physical conventions.
